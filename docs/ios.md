# iOS compatibility assessment

Raspberry can inspect the supplied decrypted LINE PLAY 10.1.0 IPA read-only; iOS patching/signing is not yet implemented in the CLI. The source archive stays read-only, and extracted binaries, disassembly and analysis databases stay outside Git.

The original November 12 assessment was static-only. On November 17 the user supplied a macOS/vphone environment and authorized autonomous iOS work, superseding the earlier deferral. Static results still cannot establish that re-signing, AirArmor, login, networking or gameplay works on a device.

## Static findings (2026-11-12)

- **[S] Baseline:** 27,000,608 bytes; IPA SHA-256 `987fefccfc235cc73fdd6363c064887272575586f334b45fcb10d213a8772532`. Bundle `jp.naver.lineplay`, version 10.1.0 / build 10.1.0.0. The package requires iOS 15.0 and supports iPhone/iPad. The main executable is arm64 for an iOS device, not Simulator.
- **[S] Decryption is not signing:** the main executable and nine embedded Mach-O frameworks have `cryptid=0` in the inspected encryption commands. Signature data remains, but no embedded provisioning profile was found. Signature validity and installability have not been checked with Apple tools.
- **[S] Protection code is present:** AirArmor-related `asdk` type information, bundle/Mach-O signature verification and debugger detection were found. `sub_101451DC0` feeds a signature-verification-failure result into event **6** in `sub_101451338`; a `sysctl`/`P_TRACED` check feeds event **8**. Other detector names are present, but names alone do not prove those checks run.
- **[S] App-level handling is present:** a worker dispatches event 6 to the callback registered during `AppController` launch. The callback reaches state setter `sub_1010A1810` (field `+52`), whose latch and game-tick consumer use mask `0x672`. Its set bits classify states **1, 4, 5, 6, 9 and 10** as abnormal, matching Android's documented set. This is not merely an SDK event list.
- **[S] State 6 has a message path:** `sub_1010A09BC` calls `sub_1010A0AF0`, which builds localized text containing `[AA-006]` and submits a generic message through `sub_1001F9A24`. It does not enter the later inspected `CNaCheatingBlockPopup` branch. That named branch's absence does not mean the generic message is harmless.
- **[?] Final effect remains unresolved:** the concrete handler behind the generic message dispatch has not been recovered. Whether a legitimate re-sign triggers event 6, and whether `[AA-006]` becomes visible or blocks gameplay, need further evidence. A verifier skip predicate tests a global for null; no platform-specific PlayCover exemption was identified.

**Comparison:** the inspected iOS build has signature verification, event dispatch and the same abnormal-state classification as Android. There is no evidence here that it has weaker AirArmor enforcement. Keep the Android state-6 patch Android-only; establish whether legitimate re-signing triggers an iOS blocker before shipping a corresponding compatibility edit.

### Main-reviewed follow-up (2026-11-17)

- **[S] Dialog path:** the abnormal-state consumer submits localized `[AA-006]` text through the common-message path to `NaCommonDialog`. Its final dismissal/repeat behavior and actual gameplay-blocking effect remain unverified. The inspected construction/submission path does not itself establish a process exit.
- **[S] Correct latch semantics:** the setter accepts a new event when the previous state is normal, including unsigned values above 10. It retains the first abnormal state. Lifecycle state-1 writes occur only when the respective protection-SDK lifecycle call returns nonzero; background/foreground transitions do not unconditionally force state 1.
- **[S/I] Patch design constraint:** both display and latch predicates use mask `0x672`. Clearing state 6 only in the display predicate would leave state 6 latched, potentially preventing subsequent unrelated abnormal events from being stored. The earlier single-site/optional-latch suggestion is therefore not an accepted compatibility design. No iOS byte patch has been applied.
- **[S] Identity:** the stock device-UUID getter is backed by the keychain, not Android's preference key. An iOS pre-engine authentication gate/getter substitution needs a separate design; do not edit existing keychain credentials or port Android's storage assumptions blindly.

Network/crypto imports, WebKit linkage and permissive ATS settings were inventoried, but actual game/login/WebView call paths and TLS verification were not traced. Android's disabled native certificate verification must not be assumed to apply to iOS.

## Routing/auth design findings (2026-11-17)

- **[V host/compile] Descriptor core:** `RBEndpoint` provides immutable v1 endpoint validation, strict regular-file loading (`endpointFromFileURL:error:`, `O_NOFOLLOW`, ≤ 4 KiB), canonical HTTPS origin, port mapping and copied native configuration using the existing C host/marker rules. Synthetic Foundation tests cover malformed JSON/numbers, booleans, NUL/Unicode/ambiguous hosts, reserved marker, port limits, symlink/directory/oversized file refusal and copy isolation; strict arm64 iOS compilation also passes.
- **[V host/compile] Unified-notice route client:** `RBNoticeRouteClient` and `RBNoticeRouteErrorAdapter` rewrite only the canonical stock unified-notice URL (`https://lan3rd.line.me/v1/lineplay/ios[?query]`) to the operator-supplied `RBEndpoint` HTTPS origin via `RBURLRewrite`, optionally forward a validated printable-ASCII `User-Agent`, keep normal platform TLS with an ephemeral cookie-/cache-/credential-free session, refuse redirects, and map HTTP 404 distinctly from transport/timeout/unexpected-status failures (refusing HTTP 200 bytes in the first-spike adapter). Synthetic `NSURLProtocol` host tests and strict arm64 iOS 15 compilation pass.
- **[V, bounded guest, 2026-11-20] Real unified-notice HTTPS request:** after proving the simulated-404 callsite diagnostic (`RBN2`: `ready=1`, `entry=1`, `outcome=1`), a private real-notice build loaded an operator-supplied `raspberry/endpoint.json` from the app bundle, sent one real `GET /v1/lineplay/ios` over normal Apple platform TLS to the configured HTTPS origin, and recorded `RBN3`: `ready=1`, `endpoint=1`, `entry=1`, `kind=1` (verified HTTP 404). Main independently inspected the 10-second screenshot (avatar introduction, no closure notice, no AA error), the fixed 39-byte `0600` summary record, unchanged bundle/data container identities, and zero new crash reports. Notice cache migration, native game API/LPN routing, Discord sign-in integration, and normal provisioning remain open.
- **[V host/compile] URL-string rewrite:** `RBURLRewrite` uses the shared host allowlist, preserves the original raw path/query/fragment and HTTP-versus-HTTPS scheme, and maps only the corresponding port. It snapshots input, returns immutable copies, leaves unrelated URLs unchanged and fails recognized malformed/missing-endpoint targets with fixed errors rather than LINE fallback. Review separated loose malformed-target recognition from strict host acceptance; encoded owned-host aliases and leading-zero ports fail closed. Host tests, strict arm64 iOS compilation and static analysis pass. This pure helper is not linked into the app and does not implement redirect policy, notice-cache migration or runtime routing.
- **[V host/compile] Auth-attempt core:** `RBAuthAttempt` generates CSPRNG state/S256 PKCE, validates exact `raspberry://auth` callbacks, expires attempts/tickets using a monotonic clock, and permits one explicit foreground exchange claim. A short synchronous writer runs under the attempt lock; cancellation serializes with it, nested commits are refused, and terminal states cannot be resurrected. Synthetic tests cover replay, malformed/oversized callbacks, cross-attempt state, clock failure, expiry and concurrency. Host tests, strict arm64 iOS 15 compilation and static analysis pass. There is no browser, HTTP exchange, credential storage or app hook in this module; it is not deployed. Writers cannot assume their side effects can be rolled back after expiry.
- **[V host/compile] Isolated exchange client:** `RBAuthExchangeClient` builds one HTTPS POST task for a claimed ticket/verifier, keeps platform trust, refuses redirects, disables cookie/credential storage and caching, and bounds the response to 4 KiB and the task resource timeout to 30 seconds. It returns only a UUID-shaped code or fixed error enum; the owning attempt must still approve any credential commit. Synthetic no-network tests cover request/configuration, limits, malformed responses, cancellation, reentrant completion and rejection of late authorization after attempt cancellation. Host gate, strict iOS compilation and static analysis pass. There is no browser, storage, startup hook or deployment; real TLS/endpoint acceptance remains untested. One task does not guarantee wire-level exactly-once delivery.
- **[V host/compile] Browser session adapter:** `RBAuthBrowserSession` and `RBASWebAuthenticationSessionDriver` keep callback URLs within the current attempt and expose only fixed outcomes. The driver requests an ephemeral session with a validated HTTPS start URL, fixed `raspberry` scheme, and an explicitly supplied owner attached to a key window in an active foreground scene. Main-thread start/cancel and per-round callback checks reject stale results. Host fake-driver tests and strict arm64 iOS 15 compilation pass. This is not linked into LINE PLAY; the correct presentation owner for the stock game is not established.
- **[V host/compile] Foreground flow composition:** `RBAuthFlowCoordinator` couples the owned browser attempt to one exchange, conditional on the same active application and presentation owner at claim and task start. Cancellation and replacement fence late results. A validated exchange stops at `ExchangeValidatedNotCommitted`: it discards the code, does not authorize the game, and does not persist credentials. Host fakes and strict iOS compilation pass; no game lifecycle integration or real exchange has run.
- **[V host/compile] UIKit lifecycle binding:** `RBAuthUIKitLifecycleBinding` starts one flow only when given an explicit endpoint and live owner. It observes only the owning app's active notification and removes its observer on terminal outcomes or main-thread stop. Temporary inactivity during a system browser sheet is not cancellation. Terminal cleanup order is covered by host tests; actual game lifecycle integration remains untested.
- **[V host/compile] Shared UIKit owner check:** browser presentation and coordinator liveness use the same public UIKit check. It requires the original loaded, visible controller view in a key window, the exact active application, and an active scene connected to that application. It does not force-load views or select an alternate window. Scene-less owners remain unsupported.
- **[V, bounded guest] Game window observation:** a loader-only diagnostic recorded an active application, an attached root view in the delegate's visible key window, and a foreground-active window scene at the stock closure notice. Main independently verified the fixed temporary record; no new crash or app-container identity change was observed. This verifies the recorded window conditions at that point, not the full presentation check later in gameplay, browser presentation inside LINE PLAY, or live sign-in.
- **[S] Native stack:** static libcurl and LPN use the main executable's shared libSystem resolver/socket imports. Main reviewed `getaddrinfo`, `gethostbyname` and `connect` stubs plus the LPN resolver's numeric-address handoff. Marker attribution remains the candidate design, not runtime-proven iOS support. Connected TCP `send` has no destination-address argument and does not need replacement for the observed address-remapping path; the Android hook set must not be copied blindly.
- **[S] TLS split:** the inspected game CurlWrapper sets peer/hostname verification options 64/81 to zero. The notice request helper instead uses synchronous `NSURLConnection`. Do not disable Apple trust or assume every stack shares curl's behavior. Actual certificate/protocol/cipher acceptance remains a device test.
- **[S/I] Native account TLS:** guest generation, session creation and session check share the unverified curl path. The static default TLS backend is SecureTransport; actual SNI when hostname checks are disabled has not been observed. Cherry's source selects the operator certificate by SNI and registers these handlers by path. A verified operator TLS name with the original HTTP Host is a candidate, not an agreed or device-tested transport. Reused-handle isolation, redirect handling and later cookie-bearing calls still need coverage before live credentials are used.
- **[V, synthetic Go loopback] TLS name versus HTTP Host:** a path-based test server accepted a request with a verified operator TLS name and a separate game HTTP Host. Method, escaped path, raw query and body arrived unchanged. Wrong-name and untrusted-root tests failed before reaching the HTTP handler. This establishes fixture behavior only, not Cherry runtime behavior or verification in the game's native curl client.
- **[S/I] Native handle isolation:** the stock wrapper resets options between jobs but does not directly clear the easy handle's connection cache. That makes reset alone insufficient evidence of TLS isolation. The two account GETs enable redirect following; the guest POST does not. A credential-bearing design must refuse redirects rather than assume they preserve the authenticated origin. The next diagnostic candidate is a fresh, non-shared easy handle for synthetic traffic only, without changing the stock pool.
- **[V, host fakes] Fresh-handle diagnostic runner:** `RBCurlProbe` checks the option sequence, fixed synthetic hostname mappings to `127.0.0.1:18443`, mandatory fixture CA path, bounded response, and cleanup using injected fake curl functions. Host certificate tests separately verify the expected name and reject a wrong name or issuer. No real curl adapter is linked; these tests do not establish native TLS, loopback confinement or safe timing alongside the game's curl initialization.
- **[S/I] Notice seam:** `LCHTTPRequestCenter` builds the production API base from `https://lan3rd.line.me/` plus `v1/`, yielding `/v1/lineplay/ios`. Authority rewrite is feasible at its URL/request helpers, but redirects, image/board requests and origin-bound cache migration still need a complete design. No blanket notice suppression or whole-cache deletion is justified.
- **[S] Credential isolation:** the stock keychain-backed UUID feeds Nelo's `forUserId:` at launch and other cookie/request state. Global UUID substitution is rejected: it could disclose a Discord-minted credential to telemetry. Main independently reviewed the narrower guest builder `sub_1006BDD4C`: its second argument supplies JSON `uniqueCode` and the corresponding `X-LINEPLAY-ACNT` derivation. Supplying a credential only there is a candidate, not an implemented hook; preserve stock keychain/telemetry identity.
- **[S/?] Startup boundary:** the engine entry `sub_101566134` runs before AirArmor initialization. Deferring it changes that ordering, and pre-engine C++ lifecycle safety is unresolved. No engine/lifecycle suppression or replay is approved. A safe async gate boundary is still under investigation.
- **[S/I] Pre-tick candidate:** main reviewed `-[CCDirectorCaller doCaller:]` and both display-link creation methods. Holding only `doCaller:` could preserve stock engine/AirArmor order and observe links recreated by interval changes. It does not prove the absence of account work during initialization or on worker threads; it is not an approved auth boundary or a deployed hold.
- **[S] Initialization dispatch:** main reviewed initial-node setup, ADI enqueue and its independent worker loop. Setup queues the goodbye/settings request before handing the scene to the director; worker processing is separate from frame-driven completion delivery. A first-tick hold is therefore not a general dispatch barrier. Actual pre-tick network timing and complete account/session coverage are untested; no request guard has been deployed.
- **[S/I] Worker pause rejected:** main reviewed both ADI processors and the outstanding-counter wait. An indefinite auth wait can prevent those jobs from completing their accounting and stall teardown. A blanket worker pause is not an accepted auth design. Native cancellation of the protected account requests is under investigation; unrelated SDK traffic and original lifecycle/protection calls must remain unchanged.
- **[S] Callback confidentiality:** `-[AppController application:openURL:options:]` logs the complete URL before forwarding to Adjust and other SDKs. A ticket-bearing callback must never enter that stock path. Do not assume `ASWebAuthenticationSession` exclusively consumes it without runtime evidence and a scoped interception plan.
- **[S/I] Other callback paths:** stock launch forwards `UIApplicationLaunchOptionsURLKey` to LineAdapter, and legacy `application:handleOpenURL:` forwards URLs to tracking. A future scoped auth-return interceptor must account for those paths, consuming even malformed returns on its reserved route before stock logging/forwarding. Sanitizing a copied launch-options dictionary must preserve every unrelated key/URL. Actual OS/session delivery and any scheme registration remain untested.
- **[SDK/V, standalone synthetic guest] Registration:** the installed `ASWebAuthenticationSession.h` documents supplying `callbackURLScheme` as an alternative to `Info.plist` registration. A separate one-shot fixture on the virtual guest used plain HTTP loopback and required both the fixed redirect and exact `raspberry://auth` denial callback. The user ran it; main verified the PASS UI and no fixture crash. This proves custom-scheme callback delivery without plist registration in that fixture only, not HTTPS adapter execution, game delegate behavior, real Discord, or end-to-end confidentiality.
- **[API documentation] Session ownership:** [Apple documents](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession) that only the calling app's session receives the authentication callback, even when another app registers the same scheme. This supports the session-based design; it is not a runtime observation of the modified game's delegate paths, nor a reason to forward confidential callbacks to its stock handlers.
- **Server coordination:** Cherry's current read-only server contract is `/Users/festivity/dev/Cherry/.agents/CONTRACT.md` on this Mac. It already permits exact `raspberry://auth` and requests the iOS platform/store route spellings, plain-HTTP paths and asset-dataset differences. Those need static/runtime evidence before declaring compatibility; no server changes have been made by Raspberry.

### Main-reviewed iOS protocol differences

These are static URL-builder findings, not a network capture:

| Purpose | iOS path/token |
| --- | --- |
| Game sublist | `/v4/home/sublist/game/iPhone` |
| Shop sublist | `/v4/home/sublist/shop/10.1.0/iPhone.nhn?parentIconId=…` |
| Tips | `/v4/cherrytip/list/10.1.0/iPhone` |
| LAN notices | `/v1/lineplay/ios` |
| First-run manifest | `/img/read/notice/ios/checkresource2.json` over the stock plain-HTTP static-image base |

The native builders obtain version `10.1.0` from `CFBundleShortVersionString`; build `10.1.0.0` is not interchangeable. The native platform token `iPhone` and manifest/LAN token `ios` are also distinct. The manifest folder difference alone does not establish asset-file or format compatibility with Cherry's Android dataset. First-run requests and resource validation still need an isolated-peer capture.

Main also reviewed the native credential path construction: `avcookie.na` belongs under this app's `NSCachesDirectory` (`Library/Caches`), not Android's `files/`. Future fresh-auth cleanup must be limited to that exact file; no cookie contents have been read. The inspected session-failure path conditionally deletes it when an internal result differs from 3001; the exact HTTP-status mapping remains unresolved.

Main-reviewed response handlers distinguish failed `checkSession` (event `10043`), successful Delete Avatar (`10054`), and refused guest generation (a separate error-dialog path with no direct cookie cleanup). Successful logout can perform broader runtime/session cleanup, but that traced cleanup leaves the cached device-UUID slot intact. These are distinct static seams, not approval to call logout cleanup for every failure or evidence of safe re-gating. Error/status mapping, UI continuation and thread affinity still require verification.

Main reviewed the response parser and common completion sink: HTTP status and body `errorCode` are separate fields. The sink initializes the body-code field to zero and the failure dispatch passes that result buffer unchanged. An HTTP 404 skips body parsing, and a native transport error without an HTTP response does not fill the body-code field. The stock `checkSession` failure callback can therefore remove its cached cookie without an authoritative invalid-session response. Do not use that cleanup as evidence of revocation or as a blanket trigger for Discord re-authentication.

For freshly allocated account requests, the reviewed preflight-failure path skips transport but still queues a normal failure completion and releases the worker's accounting. It is not an in-flight abort. Because that failure can also trigger the stock cookie cleanup, it is only a candidate when fresh sign-in is already required. Static evidence identifies the dispatch key as the route identity plus the operation ID; IDs alone are scoped to each dispatcher. The base validator has a local failure path for a null context, but replacing the worker's context would break cleanup. Request association, state transitions and runtime ordering still need verification; no guard has been implemented.

## Other runtime/signing paths (historical prerequisites)

- **Apple Silicon Mac:** needed for [PlayCover](https://docs.playcover.io/getting_started/download_playcover.html). It runs device apps through a wrapper, not a conventional iOS emulator. It is a possible launch/rendering smoke-test environment, not evidence of iPhone AirArmor behavior. LINE PLAY compatibility is untested.
- **Xcode and Command Line Tools:** provide the Apple SDK/build tools for Raspberry's own native code, plus LLDB, `codesign`, `otool` and device/crash-log tooling. Xcode's Simulator requires simulator-targeted binaries; a decrypted device IPA is not directly a Simulator build, even when both use arm64 ([Apple TN3117](https://developer.apple.com/documentation/technotes/tn3117-resolving-build-errors-for-apple-silicon)).
- **For device acceptance:** an iPhone/iPad, USB connection, compatible OS and a valid development/ad-hoc signing and provisioning path for the app and its required entitlements. Enable [Developer Mode](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device) if the device/signing workflow requires it. Keep certificates, private keys and provisioning profiles outside Git. Exact entitlement requirements must be checked before choosing a signing tool; decrypted does not mean installable unsigned.
- **Test server:** an isolated Cherry instance and a browser-trusted HTTPS endpoint for OAuth and web pages. Do not bypass certificate warnings or use Cherry's live lab data to claim acceptance.

Start with a re-signed baseline copy, then the smallest compatibility patch if one is needed, comparing logs/screens before adding routing and authentication changes. Record any modifications PlayCover itself makes. Do not enable its [jailbreak/protection bypass](https://docs.playcover.io/settings/jailbreak_bypass.html) features in an AirArmor acceptance run. Frida is optional for separate diagnostic work, not a prerequisite or an acceptance-test dependency.

PlayCover's [official releases](https://github.com/PlayCover/PlayCover/releases) should be checked again when a Mac is available; choose and record the exact version then. Do not weaken macOS system protections as a default setup step.
