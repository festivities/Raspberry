## Mission

Raspberry turns a player's OWN copy of the LINE PLAY Android client (10.1.0.0, package `jp.naver.lineplay.android`) into a client for any Cherry server. LINE PLAY (2012–2024) is a shut-down avatar game; Cherry is the community server emulator. The stock client reaches Cherry only through DNS tricks on the player's network, cannot load the game's in-app web pages (its WebView rejects Cherry's certificate), and signs in only through LINE or as a device-bound guest. Raspberry makes exactly these changes and nothing else:

1. **Endpoint.** Every connection the client would make to LINE's game hosts goes to an operator-chosen endpoint (host + port map). Never hard-coded to one server (user, 2026-11-09: "the APK can be modified to connect to ANY custom endpoint, don't hardcode to my server").
2. **Discord-only sign-in.** The only way in is Discord OAuth/SSO mediated by the endpoint, so no passwords are ever stored and the APK holds no secrets.
3. **In-app web pages** load from the endpoint (publicly trusted certificate) by rewriting the client's hard-coded LINE web URLs.
4. **AirArmor.** A re-signed APK trips the client's anti-tamper check (state 6 REPACKAGED, a blocking popup). Raspberry neutralizes that and nothing else in AirArmor.

Product shape: a patcher that runs on the operator's or player's machine against their own APK and writes a signed APK outside every repository. What the repo holds is our own code (native hook library, Java module, the patcher), patch tables (offset, expected bytes, replacement bytes) and docs. It never contains or ships LINE's code, resources or binaries.

Out of scope for v1: other client versions (the patcher is locked to one APK by SHA-256), iOS, gameplay changes, ad/analytics removal (documented, optional later), a GUI, redistributing anything LINE-owned.

## Policies (user decisions, 2026-11-09 unless dated otherwise)

- **Public repo hygiene.** This repo is public (`festivities/Raspberry`, MIT, "Patch LINE PLAY for use with Cherry"). **Never commit** any file derived from the APK (the APK, `.so`, `.dex`, smali or resources taken from it, assets, IDA databases, decompiler output; short quoted symbol names and addresses are fine), signing keys or keystores, an operator's endpoint, ports, Discord ids or secrets, device data, raw logs or captures. APK-derived material lives only under `work/`, `build/`, `out/` (git-ignored) or `%TEMP%\opencode\raspberry\`. `.gitignore` is a safety net, not the rule: run `git status` and `git diff --cached --stat` before every commit and look for anything binary or large. Add `scripts/check-repo` early (fails when the index holds a forbidden file) and run it in the gate.
- **Never redistribute LINE's code.** Releases carry only our own artifacts (patcher binary, native library and dex built from this repo, patch tables).
- **Endpoint-agnostic.** No server, host or port is hard-coded in code, docs or tests. The operator supplies the endpoint at patch time; examples use placeholders (`cherry.example.org`, `<HTTPS_PORT>`).
- **Minimal modification.** The smallest patch set that achieves the four goals above. Preference order: new code in a new dex/library of ours > a few bytes patched in LINE's binaries > smali edits of existing methods > anything touching resources or the manifest. Do not change package name, label or version. Every patch is documented in `docs/patches.md` (target, evidence, why needed, how to verify, risk) and has a test or a device check.
- **Discord-only sign-in.** No passwords, no LINE/Facebook login path, no guest account creation without Discord. The APK carries no Discord client secret and no per-operator secret (the endpoint is the only operator value).
- **Security** (applies to everything you build):
  - The hook redirects only the compiled-in LINE host set, and only to the configured endpoint. Other resolutions and connections are untouched.
  - The endpoint descriptor is validated (hostname syntax, ports 1–65535) and stored in app-private storage; no exported component, broadcast or deep link can change it.
  - Java-side calls (auth, discovery) use platform TLS validation with the public CA store. A developer pin option (`--dev-pin-sha256`) exists only for self-signed lab servers, warns loudly, and is embedded only when asked for.
  - Discord flow: PKCE (`challenge`/`verifier`), `state` that must match an attempt this device started, single-use short-lived ticket, a return target that comes back to the device that started the attempt, no token in any log. A polling variant (no return channel) would additionally need an attempt code confirmed on both screens (device-code phishing): do not build one without telling the user.
  - Patcher: verifies the input SHA-256, writes atomically and deterministically, never prints key material, keeps the keystore outside the repo with owner-only permissions, works offline.
  - No Frida/Xposed/ptrace tools in acceptance runs (Frida co-fires AirArmor callback 10 and fails the run, [AA-010]). If dynamic analysis needs them, use a scratch AVD and say so in the report.
  - Pin and verify every downloaded tool (official release pages, SHA-256), install into user space, record versions here.
- **Dependencies.** Prefer the Go standard library for the patcher. The user's dependency approval (2026-11-09) was for Cherry's `modernc.org/sqlite`; ask before adding any Go module here. Build tools (NDK, smali, apktool) are not modules, but record them.
- **Python isolation (user, 2026-11-10).** Never install pip packages into global Python. If Python dependencies are needed, create a project-local environment with `python -m venv .venv` (use the real interpreter path, not the Windows Store shim), then install through `.venv\Scripts\python.exe -m pip`. `.venv/` is git-ignored. Standard-library-only scripts need no packages or venv.
- **Commits (user, 2026-11-10).** Autonomous commits and pushes of verified Raspberry work to GitHub are authorized. Stage only your own files (`git add <files>`, never `-A`). Include a session-required attribution line only when one is actually supplied; do not invent one.
- **Live data is private.** Device data, logs, captures, keystores and the operator's values stay outside Git. Docs summarize method/path/status and protocol metadata only.

### TLS and trust
- Native curl verification is fully disabled [S] (`CurlWrapper::InitParam` 0x2a027fc setopt(64,0)+setopt(81,0); repeated in HttpSender 0x2ed3018; no CAINFO/CAPATH): any certificate works for every native game host. No pinning.
- The client's old OpenSSL offers only static-RSA cipher suites [V]; Cherry enables them with explicit `CipherSuites`.
- Java: `LinePlay.setSSLSocketFactory` installs `TLSSocketFactory` (TLSv1.1/1.2 enabler, default platform trust); `res/raw/https_keystore` is a dead resource [S]. targetSdk 33 and no `networkSecurityConfig`: the user CA store is not trusted by the Java stack.

### Login and credentials
- LINE SDK v3 is embedded (channel-apis.line.naver.jp, channel id 1350636423). The Login scene's buttons are SNS-list-driven: `NaLoginLayer::MakeLoginButton` 0x1cfe130, `SetSnsLoginUITagList` 0x1cfe4d0; the guest button is the selector `LD_GUEST`.
- **Guest flow [S, runtime-confirmed]:** `POST https://fapi.play.naver.jp/v4/account/guest/generate` with body `{"uniqueCode":"…"}` and header `X-LINEPLAY-ACNT = md5(uniqueCode + app secret)` (computed natively, `ReqAccessTokenForGuest` 0x1bbf454); the reply has `result.provider` ("lineplay") and `result.accessToken`. `uniqueCode` is the device UUID from `LoginAdapter.InfoDeviceUUID`: the saved pref **`uuid`**, else a name-based UUID from ANDROID_ID. Cherry binds `uniqueCode` to an account, so a device that presents the same code gets its account back (restoring the `uuid` pref after a wipe worked in the lab on 2026-11-08). **This is the integration point for Discord sign-in:** the endpoint mints an unguessable `uniqueCode` after Discord authentication; the patched client stores it where the stock flow reads it; the stock guest login then runs unchanged ([I], to be confirmed by the spike).
- Then `GET /v4/createSession` (cookies cc/expireAt/refreshToken/provider/udid/os/device) returns the session and `Set-Cookie AV_AUTH`, persisted as the long-term credential in the encrypted `files/avcookie.na`; relaunch uses `checkSession`. The client deletes `avcookie.na` after a 404 `checkSession`.
- `LoginAdapter.checkRootingDevice` is non-fatal in practice (the game runs on rooted emulators).

### AirArmor (anti-tamper) [S unless noted]
- `onAirCallback` 0x2a2b234 (int only) → `SetAirArmorState` 0x200cf9c (write-once latch at +0x4C, only while normal). `IsAirArmorStateNormal` 0x200cf64: abnormal = {1 FAILED_CALLING, 4 ROOTING, 5 SUSPICIOUS_TOOL, **6 REPACKAGED**, 9 INSTALLED_TOOL, 10 SUSPICIOUS_FRAMEWORK}; FRIDA=12, XPOSED=13, DEBUGGER=8 are NORMAL. Abnormal → `ShowAirArmorDetectPopup` 0x200cdf0 only (re-shown every frame; its button tears the scene down). **No process kill.** Detection lives in the packed `libm0vie.so` (entropy 7.8+, invalid JNI_OnLoad bytes, loaded ~0.18 s after start); a ptrace self-tracing child process was seen and is unattributed [?]. That a re-signed APK raises state 6 is Cherry's 2026-10-11 conclusion (the state exists and is abnormal [S]); it has never been observed on a device [I]: PLAN task 2 produces the first evidence.
- `libline-sdk-encryption.so` `Lspg.gk()` mixes the APK signing certificate with the Android id and two hard-coded secrets; it serves the LINE SDK login only and the guest path is insulated from it [S].
